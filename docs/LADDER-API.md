# Ladder A: a drafting API without workarounds

> **Draw like a draftsperson, with no helper library.** Every construction a drafter reaches for (offset, trim, fillet, hatch a bounded area, a leader, a table, a drawing scale) is one `cad.*` call, gives exact geometry, round-trips through DWG as the object AutoCAD expects, and renders the same in every viewer. The example drawings are the acceptance corpus: each rung deletes a workaround from `examples/lib/drafting.js`, re-exports the examples, and they still look the same.
>
> Builds on the construction and annotation calls added on 2026-10-13 (`construct.rs`, `annotate.rs`, `region.rs`, `spline.rs`, `dispatch_ext.rs`): intersections, fillet, chamfer, trimTo, extendTo, tangents, array, native dimensions, text alignment, hatches with holes, solid fill, splines, bulge polylines and regionClip. It also builds on the 12 example drawings and their shared library `examples/lib/drafting.js`, and on the API reference [api-surface.md](api-surface.md).
>
> **Status:** documented 2026-10-13, nothing started. The rungs are **A0–A6** and the vision is **A🎯**. Two bugs found while redrawing the examples are already fixed and are not on this ladder: bulge arcs had the wrong radius (`chord / 2 sin θ` instead of `chord / 2 sin(θ/2)`), and `regionClip` used an even-odd fill rule, so overlapping rings cancelled out (the missing wall corners in `07-floor-plan`).

## Why this is interesting here

- **Workarounds are where drawings go wrong.** Hand-computed intersections and sampled arcs are exactly where a script leaves a gap, an overlap or a faceted curve. Every call that replaces a workaround removes a class of drafting errors, for people and for language models.
- **The examples measured it.** Redrawing 12 examples with the 2026-10-13 calls cut the shared library from about 320 lines to about 194. What remains (leaders, tables, scale wrappers, fill outlines, sampled hatch boundaries) is the list of what is still missing.
- **DWG fidelity decides whether output is usable.** A drawing whose dimensions explode into loose lines, or whose Greek letters turn into `&#966;`, has to be fixed by hand in another CAD program.

## Key decisions

- **Core first, abstract geometry.** Every new operation lives in `cadview-core` behind `cad_call`, with a typed wrapper in `web/src/cad-api.ts` and an entry in `methods`. Results are exact curves (lines, arcs, splines, bulge polylines), never sampled points. Where an exact result is impossible (the offset of a spline), the result is a spline fitted within a stated tolerance, and the tolerance is part of the call's contract.
- **The examples are the regression suite.** Every rung re-exports all examples with `examples/lib/export.sh`. A changed PNG must be explained in the rung's report: an intended improvement, or a bug.
- **One helper per formula.** Geometry that exists in several copies (the bulge-to-arc conversion lived in four files) is consolidated before new features are built on it.
- **Native DWG objects when the format has them.** Dimensions, hatches and leaders are written as DIMENSION, HATCH and LEADER/MLEADER entities, not as loose lines, once A5 lands. Until then the current loose-entity export stays, and its limits are documented.

## Process

Each rung is built by a builder/tester pair, sized at about 2 weeks or less, and ends shippable. The builder (strongest model) owns the design, the core code, the docs and the report. At the start of the rung it spawns one fast, cheap tester and keeps it alive for the whole rung. The tester does the build-and-run work: core tests, the server end-to-end scripts, example re-exports, DWG reload checks and PNG comparisons. It reports what it saw, separating observed from inferred. See [LADDER-NATIVE.md](LADDER-NATIVE.md) for the full loop.

**Done** for every rung means:
- `cargo test -p cadview-core` and clippy pass.
- Each new call has unit tests, including degenerate cases.
- An end-to-end script through `POST /api/run` exercises it and saves and reloads a DWG.
- `docs/api-surface.md` and `SKILL.md` describe it.
- All examples re-export, with every changed PNG explained.

## Risks

- **DWG object fidelity (A5) is the largest unknown.** It depends on what acadrust can write: dimension styles, anonymous dimension blocks and hatch boundary paths. The first step of A5 is a writer capability check against acadrust, and anything missing is either contributed upstream or kept as the current loose-entity export with a documented limit.
- **Spline offsets are approximations by nature.** The tolerance must be part of the API contract and the docs, and the fitted spline should be cached, not refitted on every render.
- **Curved booleans (A6) are a known hard problem.** Refitting arcs after a polygon overlay can misassign edges near tangencies. A6 ships with a corpus of tangent and near-tangent cases, and falls back to the polygonal result with a reported warning instead of guessing.
- **Behaviour changes ripple into the examples.** A3's scale handling and A4's exact hatch boundaries change pixels in many drawings. The re-export comparison has to separate intended changes from regressions, which costs review time on every rung.
- **Two renderers double the fidelity work.** A1 has to be done in both Vello and egui. If the native app (LADDER-NATIVE) settles on Vello only, egui fidelity work can stop at "readable".
